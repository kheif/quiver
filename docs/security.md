# Security of the v1.6 release

This file works through the risks that v1.6 adds. Each has its mitigation and the test that holds it; a risk without both would block the release. [TASK70](../tasks/TASK70-security-review.md) completes the file for the whole product. The practices for users are on the website's security page (`web/src/content/docs/docs/project/security.md`); the policy for reporting a vulnerability is [SECURITY.md](../SECURITY.md).

## 1. Skills that the assistant loads without asking

A *Searchable* skill is not listed, and the assistant loads it with `get_skill` as soon as a search finds it, without asking the user. Assigning the skill is the statement that the user trusts it. What this adds, and what holds it:

| Risk | Mitigation | Test |
|---|---|---|
| A whole source becomes Searchable by one careless yes, so skills nobody read are loaded without asking. | `quiver source add` asks once whether to make the skills Searchable, with the default no, and says it prints the command that undoes it. Without a terminal and without `--searchable` nothing is assigned. The note "skills give instructions to your assistant and may contain scripts" is printed first. | `TestOfferSearchable`, `TestSourceAddSearchable` (`internal/cli/searchable_test.go`) |
| A source update changes a Searchable skill that was reviewed before. | `quiver update` previews the changed files of every assigned skill, Searchable ones included, marks scripts as needing review and asks before it applies; `quiver pin` keeps a skill at a reviewed commit. | `TestUpdateWithSearchableSkills` (`internal/cli/searchable_test.go`) |
| The assistant is talked into rewriting a Searchable skill, and loads its own rewrite without asking next time. | `update_skill` refuses a Searchable skill, as it refuses an always-on one; the user changes it with `quiver edit` or first lists it with `quiver add <id>`. | `TestUpdateSkillRefusesSearchable` (`internal/server/searchable_test.go`) |
| Another machine makes skills Searchable and a `quiver sync` pulls them in unnoticed. | The review of `quiver sync` lists Searchable skills that arrive and changes to them, and asks before it pulls. | `TestSyncReviewsSearchableChanges` (`internal/cli/searchable_readers_test.go`) |
| `search_skills` exposes skills nobody assigned. | It returns only Searchable skills of the folder, at most 10. `get_skill` still reads the whole library by ID, which the security page states; a skill that is not assigned loads with a note that says so. | `TestSearchSkillsReturnsOnlySearchableSkills` (`internal/server/search_test.go`), `TestSearchableSkillIsLoadedNotListed` (`internal/server/searchable_test.go`) |
| Skills the user writes are Searchable by default, so a skill that the user did not read closely is loaded without asking. | Only `quiver new`, `quiver import` and the panel's `n` and `i` do this; the skill is the user's own. `create_skill` (the assistant writes) stays *On demand*, listed, and its result tells the user how to make it Searchable; `quiver fork` copies the level of the original. | `TestCreateSkillStaysOnDemandAndSaysHowToMakeItSearchable` (`internal/server/cue_test.go`), `TestNewSaysItIsSearchableAndHowToMoveIt`, `TestForkKeepsTheLevelOfTheOriginal` (`internal/cli/cue_test.go`) |
| The search cue is text that reaches the model in every session. | It is a fixed text of Quiver, names no skill, and is passed in its own `<quiver-search>` block; the text that reaches the model from skills is cleaned and cannot write Quiver's tags. The check that decides whether to pass it reads only `registry.json`. | `TestCueInEveryDeliveryPath`, `TestCueReadsNoSkillFile` (`internal/server/cue_test.go`) |

**Backlog B07** (approval for skills the assistant creates with `create_skill`) is not changed by this release: a skill created through the MCP server is *On demand* and listed, never Searchable, so it is not loaded without a decision of the user. B07 stays with TASK70, which decides the review step for what `create_skill` writes.

## 2. The download of the model file and the loader that reads it

The `local` search engine needs one file of 91 MB, downloaded once by `quiver engine setup` after the user says yes.

| Risk | Mitigation | Test |
|---|---|---|
| A wrong or malicious file is accepted because the host is trusted. | The hash decides, not the host. The two files (`model.safetensors`, `tokenizer.json`) are downloaded from pinned URLs of one fixed revision (the full 40-character commit, never a branch), to temporary files, checked against their pinned size and SHA-256 and only then moved into place. A wrong hash, a cut download and a file larger than announced are deleted. | `TestEnsureModelFilesRejectsABadDownload` (`internal/library/modelsetup_test.go`), `TestEngineSetupRejectsABadDownload` (`internal/cli/enginesetup_test.go`) |
| A redirect leads to plain HTTP or to an endless chain. | Redirects are followed only over HTTPS and at most three times; the address itself must be HTTPS. | `TestEnsureModelFilesRedirects`, `TestEnsureModelFilesRefusesAnHTTPAddress` |
| The pinned constants drift from what was reviewed, or are replaced at run time. | They are constants of `internal/library/models.go` that only a test can replace (no environment variable, no flag in the shipped binary); a test compares them with the figures recorded in `docs/spike-discovery-results.md`. The build tag `tinymodel`, which trusts a test host, is never part of a release. | `TestPinnedModelMatchesTheSpikeResults`; `go vet -tags tinymodel` is separate from the release build |
| The setup runs a program or contacts another address. | It installs and starts no runtime: the model runs inside the Quiver process. The only network use is the download; a test host fails any other dial, and a search makes no network call. | `TestEngineSetupEndToEnd` (`internal/cli/enginesetup_test.go`), `TestSetupRunsNoCommand` |
| The user is surprised by the download. | Nothing starts without a yes: the setup asks once with the default no, `--yes` answers it, no terminal means nothing changes, and the offer after the first Searchable skill is made once. The question names the size, the disk space, the memory and that the download is the only thing that leaves the machine. | `TestEngineSetupAsksOnceAndDefaultsToNo`, `TestEngineSetupWithoutATerminalChangesNothing`, `TestOfferAfterTheFirstSearchableAssignment` |
| A file the user put there by hand is deleted, or a file that was replaced is trusted. | A hand-placed file is accepted only with the pinned hash and is never deleted by `quiver engine remove`, which deletes only what the settings file records as downloaded and that still has the recorded hash. | `TestEngineSetupAcceptsAFileByHand`, `TestEngineRemoveDeletesOnlyWhatQuiverDownloaded`, `TestEngineRemoveNeverDeletesAFileByHand` |
| A malformed weight file crashes the process or makes it allocate without bound. | The loader (`internal/embed`) checks the header, every tensor's name, type, shape and offsets, the total size and the dimensions against the fixed shape of the model, and refuses an oversized file, before it maps or reads a weight. The tokenizer file is checked too. A model that fails its check makes the search run as `words` with one line, and `quiver doctor` names the step. | `TestLoadChecks`, `TestLoadRefusesAnOversizedFile`, `TestLoadTokenizerChecks` (`internal/embed/embed_test.go`) |
| The model file is replaced after the check. | The weight file is mapped read-only and only ever replaced by a rename; a search checks its size, `quiver doctor` and the setup hash it. | `TestLocalEngineRefreshesWhatChanged` and the doctor tests (`internal/library/local_test.go`, `internal/cli/engine_test.go`) |

**The one open dependency is the address.** The file is served by huggingface.co. If the address changes, the file is removed or the machine cannot reach it, the setup stops with the reason, the engine stays `words` and searching keeps working; a file placed by hand with the pinned hash works without the address. Whether the project also keeps a copy in its release assets, as a second pinned URL, is the maintainer's decision before the tag (TASK62.10, item 8). It is a risk of availability, not of integrity: whichever host serves the file, the pinned hash decides.

## 3. A search makes no network call

Search, `search_skills` and the panel never touch the network: the model runs inside the process, the vectors are a file of the Quiver home (`cache/embeddings.json`, derived data, never synced or committed), and the settings file (`state/search.json`) belongs to the machine. The downloads that Quiver makes are the git operations on sources and the remote of `quiver sync`, the daily release check (off with `QUIVER_NO_UPDATE_CHECK=1`) and the model download of section 2.

| Risk | Mitigation | Test |
|---|---|---|
| A search sends the query or the skills somewhere. | No search code path opens a connection; a test transport that fails any address proves the setup contacts only the model host and that a search afterwards makes no call. | `TestEngineSetupEndToEnd`, `TestEngineSetupThroughTheBinary` (`e2e/flows_test.go`) |
| A file of a newer or an older Quiver is read and written back damaged. | Every file carries a format version; a settings file or registry with a newer version is refused with the version needed and left as it is, and a derived file under `cache/` of another version is ignored and rebuilt. The golden home of v1.5.0 is read and upgraded by the current code. | `TestGoldenHomeV150` (`internal/cli/formats_test.go`), `TestSetupRecordKeepsTheOtherKeys` (`internal/library/modelsetup_test.go`) |

## What this review does not cover

The review of the whole product (the sources a user adds, the hooks, the install scripts, the sync remote, the prompt-injection paths of skill text) is TASK70. v1.6 does not change the install scripts, the release workflow or the hooks' handling of text beyond the cue.
