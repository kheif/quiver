# TASK62.6: Local vector search

**Phase:** Phase 7b: Skill discovery (v1.6)

**Part of:** [TASK62](TASK62-finding-unassigned-skills.md): Finding unassigned skills

**Status:** ✅ Done

**Depends on:** TASK62.1, TASK62.5

The `local` engine: search by meaning ("send a note to the team channel" finds the Slack skill) with a small embedding model that Quiver runs itself, inside its own process, in plain Go. There is no server, no runtime, no native library and no cgo, and a search makes no network call. The model is all-MiniLM-L6-v2 (22 million parameters, English): a weight file of 91 MB that TASK62.7 downloads once into `~/.quiver/cache/models/all-minilm-l6-v2/`. TASK62.1 measured it (docs/spike-discovery-results.md): fused with the ranked word search it found the fitting skill for 93% of the English queries of its test half, against 73% for the word search alone. It understands English only; a query in another language gets the `words` matches. Other models (the user's own, models of other languages, a server on a loopback address) are a later task (backlog B20); the settings block is built so that they can be added.

1. **Setting.** `engine` accepts `local`; the settings file (TASK62.5) gets a `local` block with `model` (the folder under `cache/models/`, default `all-minilm-l6-v2`) and `minScore`. Nothing else is configurable now.
2. **The model code.** `internal/embed`, plain Go, no cgo and no assembly. It reads `model.safetensors` (float32) and `tokenizer.json` (WordPiece with lower-casing, accent stripping and a split at punctuation, as BERT does; the accent stripping needs Unicode decomposition, so `golang.org/x/text/unicode/norm` becomes a dependency of the module, the spike's own `go.mod` already has it, and tasks/decisions.md gets a row for it), runs 6 transformer layers of 384 values (post-LayerNorm, GELU) with the linear layers spread over all cores, takes the mean of the token vectors and normalises it; a text is cut at 256 tokens. The weight file is mapped, not read, where the system allows it (a Unix call); where it does not, the file is read (191 MB of memory in the spike), and TASK65 settles Windows. The file is mapped read-only and is only ever replaced by a rename (TASK62.7), never changed in place, so a mapped file cannot shrink under a running process; the one conversion from bytes to float32 values is kept in one function that checks alignment (it copies when the data is not aligned) and is the only use of `unsafe`. The loader checks the name, type, shape and offsets of every tensor against the size of the file before it uses them: a malformed, cut or oversized file is an error that names the check, never a crash or an unbounded allocation. An embedding that fails leaves the index as it was.
3. **Index.** `~/.quiver/cache/embeddings.json`: a format version, the model name, the pinned SHA-256 of its weight file (the file itself is hashed by the setup of TASK62.7 and by `quiver doctor`, not at every search; a search checks only that its size equals the pinned size), the vector dimension (384) and, per skill, its ID, a hash of the embedded text (ID, name and description) and its vector. Derived data: not synced, not committed. An index of another format version, another model file or another dimension is ignored and rebuilt. Entries of skills that no longer exist are dropped when the file is next written. The index covers the whole library, so the CLI and the panel can use it; the engine receives the set of skills to search (TASK62.5) and ranks and caps within that set, so `search_skills` is limited to the Searchable skills of the folder before anything is cut. A plain file is enough: 262 vectors of 384 numbers are about 1 MB as JSON, and the comparison is a loop.
4. **Indexed when a search needs it.** A search compares the hashes of the library with the index and embeds what is missing or changed: a new skill, an edit by hand, a `git pull` inside a source, a skill that arrived while the model file was missing. No command embeds at the moment it adds a skill, and nothing is embedded or printed under the engine `words` or while the model file is missing (`quiver doctor` names the missing file).
   - **Batches and locks.** The embedding runs outside the home lock. After each batch of 8 skills the process takes the lock (`fsutil.WithLock`, which blocks and is not re-entrant, so it is held only for this step and never around a call that locks again), merges the batch into the current file and writes it atomically. Two processes that embed at the same time may do some work twice, and neither loses the other's entries; a process that is killed loses at most one batch.
   - **Cold or stale index.** One skill costs about 0.1 s on 8 cores and 0.4 s on one (TASK62.1, Apple M1); 200 new skills take about 20 s on 8 cores and 75 s on one. A `quiver search` process builds the missing part synchronously for up to 60 seconds with a progress line on stderr; after that it answers with the vectors it has, says that the index is incomplete and leaves the rest for the next run. `quiver engine reindex` rebuilds the whole index without that limit. The long-lived processes (the server, the panel) build in the background and meanwhile answer with the vectors they have and with `words`. A failed embedding is one line, and the search falls back to `words`.
   - **One model per process, no central process.** Each Quiver process (the CLI, one server per assistant session, the panel) maps the weight file itself when it first needs a query vector. The operating system shares the mapped pages, so several processes do not each hold a copy of the weights; this task measures the memory of five processes searching at once with the real file and writes it in the README. A process that has the index needs the model only for the query: about 20 ms on 8 cores, 75 ms on one. Quiver starts no background process; a central one would be a service to start, stop, upgrade and secure, for a saving that the shared pages already give. tasks/decisions.md records this.
5. **Loading and failure.** The model is loaded at the first search that needs it (a mapping and a table of words: tens of milliseconds), so there is no warm-up and no wait. A model file that is missing or fails its check gives the `words` matches with one line (TASK62.5); the engine stays `local`, and `quiver doctor` names the missing step, which TASK62.7 repairs.
6. **Query and fusion.** The query is embedded and compared by cosine similarity. Candidates below `minScore` are dropped; the default `minScore` of the model comes from the calibration of TASK62.1, and an explicit value in the file wins. At most 50 vector candidates remain. They are combined with the `words` matches by reciprocal rank fusion with k = 60 over two orders: the order in which `words` returns its matches (matches with the same rank and score share a rank), and the order of the vector scores. Ties in the fused score break by vector score, then by ID. Matches of the exact-name tier stay above everything the fusion produces. A skill found only by vector gets a new rank `RankMeaning` after the last `words` tier, and in the vector order a skill without a vector score comes after those with one. `Match.Rank` keeps the `words` tier for display.
7. **Panel.** A vector call never runs on the keystroke path (it takes 20 to 75 ms of processor time). `Backend.Search` takes a context, the panel also gets a synchronous call that only runs `words`, and every place that calls `refilter` in `internal/tui/tui.go` (typing, a change of view, a reload, and a change of another section's query) handles a pending search: after a short pause in typing the panel starts it as a command, shows the `words` results at once, replaces them when the fused results arrive, and drops a reply whose query is no longer the current one.
8. **Doctor.** `quiver doctor` reports the model file (present, hash intact), the dimension, the number of indexed skills and how many are stale.
9. **Docs.** tasks/data-model.md gets a `cache/` section that covers `cache/hook`, `cache/models/` and the index. The README gives the measured rates of `local` and of the ranked word search side by side, the sizes, and the memory of five processes. The guide page "Finding skills" (TASK62.4) gets the engine and says that it understands English. `reference/files.mdx` lists `cache/embeddings.json` and `cache/models/`, and the security page ("Network access") says that a search makes no network call and that the only call is the one download of TASK62.7.

**Done when:** tests cover: golden token ids and vectors of the model (a cosine of at least 0.9999 against the reference vectors) for texts with accents, punctuation, an empty text and a text over 256 tokens; a malformed, cut and oversized weight file, each check of the loader, with no crash and no large allocation; the fusion (an exact name stays first even when its vector rank is low; a query that fits nothing returns only `words` matches; equal `words` ranks share a rank; a vector-only match gets `RankMeaning`; a skill without a vector score); `minScore`; no embedding and no output under the engine `words` or with a missing model file, no embedding at the moment a command adds a skill, a failed embedding that falls back to `words` with one line, and an interruption after a save; a batched incremental refresh after a changed, a deleted and a pinned skill, and the dropped entry of a deleted one; a changed model file and a changed dimension; a cold index in the CLI (the progress line, the 60 seconds, the incomplete message) and in the server; two processes writing at once with the embedding outside the lock and the merge after each batch; a process killed between two saves; `quiver engine reindex` rebuilding the whole index; a model file that is missing or fails its check (`words` and one line, `doctor` names the step); an index of another format version; the panel dropping a stale reply and showing `words` first for typing, a change of view, a reload and a change of another section's query; and `doctor`. The tests use a tiny model with random weights that a test generates, so they do not need the real file. An end-to-end test runs `engine use local`, `engine reindex` and `search` against that tiny model. A test that only runs when an environment variable names the real model file checks a few known queries, and before the release the memory of five processes searching at once is measured with it and recorded in this task.

## Measured

On an Apple M1 (8 cores), macOS, the real all-MiniLM-L6-v2 files (the pinned size and both hashes verified by `quiver doctor`), a library of 263 skills, the English queries of the spike's test half (`TestRealModelOnTheSpikeQueries`):

- A fitting skill among the first five matches: 55 of 60 (the spike measured 56 of 60); queries that fit nothing and return nothing: 22 of 27 (the spike: 22 of 27).
- `quiver engine reindex`: 23 s for 263 skills (117 s of processor time).
- One `quiver search`, with the index and the query embedded: 0.12 s, 74 MB resident (maximum resident set size), 21 MB peak memory footprint. The `words` engine alone: 0.09 s, 25 MB resident.
- Five processes searching at once: 0.17 to 0.19 s each, 74 MB resident and 21 MB footprint each; the mapped weight file is shared between them.
- The golden vectors of `internal/embed` were made by the spike's implementation, which TASK62.1 checked against Ollama's all-minilm (cosine 1.00000 for 472 texts); the port gives a cosine of at least 0.9999 against them for texts with accents, punctuation, an empty text, a text over 256 tokens and a Chinese text.
