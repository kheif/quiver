# TASK62.7: Guided setup of the local model

**Phase:** Phase 7b: Skill discovery (v1.6)

**Part of:** [TASK62](TASK62-finding-unassigned-skills.md): Finding unassigned skills

**Status:** ✅ Done

**Depends on:** TASK62.1, TASK62.4, TASK62.6

The user answers one question; Quiver does the rest: it downloads the model file, builds the index and checks that search works. Quiver installs and starts no runtime and runs no command: the whole setup is the download of one model file (TASK62.6 runs the model inside the Quiver process).

1. **Entry points.** `quiver engine setup` runs the setup. After the first Searchable assignment that the user makes in a terminal (`quiver add --searchable`, a source added with a yes, and `quiver new` and `quiver import` once TASK62.8 makes them assign Searchable), while the engine is `words` and the offer has not been made, Quiver offers the setup once, with the default "no", and records that it offered (`offered` in the settings file) so it does not ask again; a pointer stays in the panel's Health section and in `quiver status`, whose one line of advice, "search by meaning: quiver engine setup", shows while Searchable skills exist and the engine is `words`. Nothing starts a setup without the user's yes.
2. **The question.** Before it changes anything Quiver says what will happen and asks once, with the default "no": the model (all-MiniLM-L6-v2, English), the download size (91 MB), the disk space (the file and an index of about 1 MB), the memory a search uses while the model is loaded (up to about 85 MB, mostly the mapped weight file that the system shares between processes; TASK62.6 measures it), and that the only thing that leaves the machine is the download of the model file; a search itself makes no network call. `--yes` answers it. Without a terminal and without `--yes`, Quiver changes nothing and prints the command that would do it.
3. **The download.** The two files that the loader reads (TASK62.6), `model.safetensors` and `tokenizer.json`, are downloaded over HTTPS from pinned URLs of one fixed revision, the full 40-character commit (never `main`; docs/spike-discovery-results.md records it with the size and the SHA-256 of both files), to temporary files, checked against their pinned sizes and SHA-256, and moved atomically into `~/.quiver/cache/models/all-minilm-l6-v2/`. A wrong hash, a cut download or a file larger than announced is deleted and ends the setup with the reason. Redirects are followed only over HTTPS and at most three times (the host that serves the large file is not the host of the URL); the pinned hash decides whether a file is accepted, so the host that serves it need not be trusted. No command is run and no other address is contacted. The pinned URLs, sizes and hashes are constants in the code that only a test can replace (an unexported variable, no environment variable, no flag). A test compares the constants with the figures in docs/spike-discovery-results.md, so the two cannot drift, and the one real download is made by hand in the release check of TASK62.10.
4. **Risk: one address.** The file is served by huggingface.co. If the address changes, the file is removed or the machine cannot reach it (offline, a company network that blocks it), the setup stops with the reason and the engine stays `words`; searching keeps working. Before v1.6.0 the maintainer decides whether the project also keeps a copy of the file in its own release assets, as a second pinned URL that is tried after the first with the same hash check, and with the Apache-2.0 license text of the model next to the file (TASK62.10 records the decision). Until then this is the open risk of the download.
5. **By hand.** A file that the user puts in `~/.quiver/cache/models/all-minilm-l6-v2/` (a machine without access to the address, a company mirror) is accepted when its hash matches the pinned one; `quiver engine setup` then says so and skips the download. A file with another hash is refused with the pinned hash in the message.
6. **Index and check.** The index of TASK62.6 is built with a progress line, and then the check runs through the vector path alone, with no fall-back to `words`: it embeds the name of one of the user's skills and the skill must be among the first five of the library. A failed check leaves the engine at `words` and says which step failed.
7. **Record.** The settings file gets `engine: local`, the `local` block and, for what Quiver itself downloaded, `installed` (the files and their hashes). Quiver prints a summary: what it did, where, how much space, how to undo it.
8. **Undo.** `quiver engine use words` switches back and keeps everything. `quiver engine remove` deletes the index and, for what the settings file records as downloaded by Quiver, asks before deleting the model files. A file that the user put there by hand is never deleted.
9. **Repair.** `quiver doctor` reports each link of the chain (model files present and their hashes intact, index fresh); `quiver doctor --fix` on the command line repeats the missing step with the same question. The panel's `Fix` never starts a download; it points to the command line.
10. **Panel.** The panel shows the engine and the state of the chain in its Health section; the setup itself stays on the command line, because it downloads a file.
11. **Docs.** The README and the guide page "Finding skills" (TASK62.4) describe the setup, what it downloads, the sizes, that the model understands English only, how to place the file by hand and how to undo; the help text of `quiver engine` lists its commands. The website's security page ("Network access") names the one download of the model file and says that a search makes no network call, and the doctor lines follow the `ok`, `warn` and `error` format that the panel's Health section parses (`internal/cli/tui_parity_test.go`). tasks/decisions.md records that Quiver installs no runtime and runs the model in its own process.

**Done when:** tests, with a fake download server that serves a tiny model under test hashes, cover: the setup end to end; a hash that does not match, a cut download and a file larger than announced (deleted, engine stays `words`); a redirect to another host over HTTPS (accepted, hash checked), a redirect to plain HTTP and a fourth redirect (refused); the download being the only network call and a search making none (a test dialer fails any other address); no command run by any step (a command runner that fails the test when called); the question being asked once and `--yes`; no terminal without `--yes` (nothing changes, the command is printed); the offer after the first Searchable assignment (made once, recorded in `offered`, never repeated, default no, nothing without a terminal); a file placed by hand, accepted by its hash and refused by another; a check that fails because the vector path is broken while `words` still finds the skill (the engine stays `words`); the record of what was downloaded; `engine remove` removing only what Quiver downloaded and asking first; `doctor` and `doctor --fix` for each broken link; the advice line of `quiver status` (shown while Searchable skills exist and the engine is `words`, and never starting a setup); `engine use words` keeping everything; the Health section of the panel; and the panel's `Fix` running nothing of the setup. An end-to-end test runs the setup through the binary against the fake server. Before the release the maintainer runs the setup against the real address on a machine for each system that is available and the result is written in the task; a system that could not be tried is documented as such.

## Built

- `quiver engine setup` asks once (default no, `--yes`, nothing without a terminal), downloads the two pinned files, builds the index, checks the vector path alone and then writes `engine: local`; `quiver engine remove` deletes the index and, after asking, only what the `installed` record says Quiver downloaded. A failed step leaves the engine at `words`; what was already downloaded stays recorded.
- The offer after the first Searchable assignment (`quiver add --searchable`, a source added with a yes) is made once and recorded in `offered`. `quiver new` and `quiver import` do not assign Searchable yet; TASK62.8 adds the offer there.
- `quiver doctor` shows each link, `quiver doctor --fix` repeats the missing step with the same question in a terminal; the panel's `Fix` runs no download and the Health item points to the command line. `quiver status` and `quiver doctor` advise the setup while Searchable skills exist and the engine is `words`.
- The pinned URLs, sizes and hashes are constants of `internal/library/models.go`; a test compares them with `docs/spike-discovery-results.md`. A fresh download of `tokenizer.json` on 2026-11-22 has the pinned size and hash, which the results had taken from the spike's copy. Tests replace the download only through `RegisterModel` and `SetModelTransport`; the binary built with the tag `tinymodel` can trust the fake host of the end-to-end test, and the production binary cannot.
