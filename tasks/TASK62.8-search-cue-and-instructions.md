# TASK62.8: Search cue and default level of new skills

**Phase:** Phase 7b: Skill discovery (v1.6)

**Part of:** [TASK62](TASK62-finding-unassigned-skills.md): Finding unassigned skills

**Status:** Todo

**Depends on:** TASK62.1, TASK62.3, TASK62.4, TASK62.5

The assistant has to know that searchable skills exist and when to look for one, without a list of them. Quiver does not search on every message: it sees only the message, and the assistant knows the topic of the conversation, so the assistant decides and forms the query.

1. **Instruction.** The server instructions, the description of `search_skills` and the session-start text say: some skills are not listed because the user made them searchable; when the topic of the conversation, not only the last message, calls for something that such a skill could cover (writing for a tool or a channel, working with a service, a file type, a style guide), call `search_skills` with the topic in a few words, before starting and again when the topic changes; load a fitting skill with `get_skill` without asking, because the user chose it; a plain question about the project needs no search. The final wording is the one that did best in TASK62.1: the second wording of docs/spike-discovery-results.md (the query names the product, tool, service or channel and what is produced, and one more search from another angle if nothing fits), which met the threshold with the ranked word search where the first did not. The sentence of the server instructions about `list_skills` ("If there is no <quiver-skills> block, call the list_skills tool") stays as it is, because an assistant without a hook never gets the block and depends on it.
2. **The cue.** Whenever the folder has at least one Searchable skill (global or project, at the level of TASK62.2), the session-start text ends with the cue of item 1: a short paragraph, no names, no descriptions, after the always-on skills and the catalog if there are any. When nothing is listed in the folder, the cue says so ("no skills are listed in this folder"), so that the existing instruction to call `list_skills` when there is no `<quiver-skills>` block does not send the assistant to a tool that has nothing to say; TASK62.1 measures this in its primary cell. The server instructions mention searchable skills only when the folder has some, by the same check. When the folder has none, nothing is added. A folder in which nothing is listed and something is searchable gets the cue alone, where the hook printed nothing before; `buildSessionContext` no longer depends on the catalog having a line.
3. **Cheap check.** Whether the folder has a Searchable skill is answered from the lists of `registry.json`, without reading a skill file, so the hook does not get slower with the size of the library: a test with an unreadable skills folder shows that no skill file is read. TASK69.3 sets the time budget of the hook later. `PartsNeeded` and `BuildSessionContext` use the same check.
4. **Tool description.** TASK62.5 changes what `search_skills` searches and how its description reads (it searches the skills the user made searchable and does not return the others, replacing the text of TASK45); this task adds the cue to that description. `get_skill` of a skill that is not assigned keeps its "not assigned" note, and still loads any skill of the library; the website's security page says what that exposes and that `search_skills` returns only Searchable skills.
5. **Assistants.** The assistants with a session-start hook (Claude Code, Codex, Cursor, Antigravity, VS Code) get the cue from the hook and from the server instructions; an assistant without a hook gets it from the server instructions only, and Claude Desktop, which drops them, gets none, so the user has to name Quiver there. The website's `assistants.md` lists which assistants get the cue and marks Claude Code as measured and the others as not yet measured (TASK62.1 measured Claude Code only). Any other assistant that can run an MCP server works through the tool and the instructions.
6. **Docs.** The README, the website's `concepts/mcp-delivery.md` and PROJECT.md's description of the session-start text mention the cue.
7. **Default level of skills the user makes.** `quiver new` and `quiver import` assign the skill as *Searchable* in the scope each uses today (the project for `new`, with `--global` for every folder and `--none` for nowhere; the scope `import` asks for, with `--global` as its default), where they assigned it *On demand*, and only for a skill they assign newly: a skill that is already assigned, which `import` reuses, keeps its level. The first-run import of `quiver init` is an import and does the same. The output says so and that `quiver add <id>` moves the skill to another level. A skill that the user wrote or imported is their own, so it is trusted in the same way. `create_skill` is not changed: a skill that the assistant writes is *On demand* in the scope it is created in, as today, until the user decides otherwise; its result says that `quiver add <id> --searchable` makes it searchable. `quiver fork` is not changed: the copy takes the places and levels of the original, as its help says. In the panel, `n` creates a skill as Searchable (TASK58.1 says "on demand (the default)") and `i` imports as Searchable, and the lines of the CLI output that the panel reads (`internal/cli/tui.go`, `NewSkill` and `Import`) keep working with the new wording. This default is right only if the measured rate of finding a Searchable skill meets the threshold of TASK62 (TASK62.1), which is why it ships together with the cue and not before it. The README, `quiver new --help` and `quiver import --help` say so.

**Done when:** tests cover the instruction text in each delivery path (server instructions, tool description, session-start text, hook parts), the unchanged `list_skills` sentence, the cue after the always-on skills and the catalog, the cue alone when nothing is listed, no cue when nothing is Searchable (`TestHookNothingAlwaysOn` in `internal/cli/hook_test.go`, whose library holds one unassigned skill and expects no output, stays valid, and a new case with a Searchable skill expects the cue), the cue for a project-only and a global-only Searchable skill, the unchanged note of `get_skill` for a skill that is not assigned, the folder-level of a skill that is Searchable in one scope and listed in the other (cue present, listed skill not searched), the cue text for a folder in which nothing is listed, the server instructions with and without a Searchable skill, and no skill file being read by the check (an unreadable skills folder). Tests also cover `new` (also with `--global` and `--none`), `import` (also for a skill that is already assigned), the first-run import of `init`, `create_skill` and `fork`, and the panel's `n` and `i` with the output lines it reads. An end-to-end test (TASK30) runs the hook through the binary for a home with a Searchable skill and one without.
