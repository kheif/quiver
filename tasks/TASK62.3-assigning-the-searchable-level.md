# TASK62.3: Assigning the Searchable level

**Phase:** Phase 7b: Skill discovery (v1.6)

**Part of:** [TASK62](TASK62-finding-unassigned-skills.md): Finding unassigned skills

**Status:** Todo

**Depends on:** TASK62.2

The commands that move a skill to the Searchable level (see TASK62.2 for the level and the registry). This task changes no default: what `quiver new`, `quiver import` and the panel assign when the user says nothing changes in TASK62.8, in the same task that tells the assistant to search, because the two work only together.

1. **Assigning.** `quiver add <id>... --searchable` assigns Searchable to this project, with `--global` to every folder; it removes the skill from the served list of that scope, always-on mark included. `quiver add` without the flag is *On demand* and removes the skill from the Searchable list of that scope; it keeps an always-on mark, as today. `--searchable` with `--always` is an error. `quiver add --source <name> --searchable` (with `--global`) makes the skills of a source Searchable, and only those that are not yet assigned in that scope: a skill that is listed or always on keeps its level. `--source` without `--searchable` is an error, and `--source` takes the place of the IDs, so the `Args` rules of `add` and `remove` change. `quiver remove <id>...` removes a skill from every level of the scope, and `quiver remove --source <name>` (with `--global`) removes every skill of that source from the scope at every level. A skill is *assigned* when it is at any of the three levels, so `quiver list --unassigned` leaves Searchable skills out. A move says what it did. The JSON outputs that name where a skill is assigned keep their current fields, which keep describing served assignments, and gain a separate field for the new level (a field `level` next to `here` in `quiver search --json`, and a field `searchable` in `quiver list --json` and `quiver where --json`). `quiver list` and `quiver where` show the level of each scope as stored, and `quiver status` shows the level in this folder (the panel does the same, TASK62.4 item 3).
2. **Adding a source.** `quiver source add` asks once, in a terminal, when the source has at least one skill, after it has printed the number of skills and the note that skills can contain scripts, which now says to read them with `quiver show <id>` first: "make the N skills searchable in every folder? The assistant will then load them without asking when a search finds them. [y/N]". The default is no. When the user says yes, all the skills become Searchable at once, and the output says how many and prints the command that undoes it, `quiver remove --source <name> --global`, which removes exactly these skills because nothing else of a new source is assigned. `--searchable` answers yes; without a terminal and without the flag nothing is assigned. A source that is already added is handled by `quiver add --source <name> --searchable`. `quiver update` previews changes to Searchable skills like those of every assigned skill, and waits for a yes when they change, as `quiver update` does for a source today, with one question for the source that lists what changed, not one for every skill; a skill that a source adds later is not Searchable until the user chooses.

**Done when:** tests cover `add --searchable` with and without `--global`, with `--always` (error), moving a skill from and to each level, `add --source` with and without `--searchable` and leaving listed skills alone, `remove` from each level and `remove --source` with and without `--global`; `list --unassigned`, `list`, `where`, `show`, `status` and `search --json` with the new fields and the old ones unchanged; `source add` with the question answered yes and no, the default, a source without skills, the printed undo command (project and global), `--searchable`, no terminal (the prompt unit-tested with `interactive` replaced, because the end-to-end harness has no terminal); an update that adds a skill to a source after the user said yes (not Searchable) and one that changes a Searchable skill (preview, waits for a yes). An end-to-end test (TASK30) runs `source add --searchable`, `source add` without a terminal, `add --searchable`, `list`, `where` and `remove --source` through the binary.
