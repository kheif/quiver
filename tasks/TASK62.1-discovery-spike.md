# TASK62.1: Discovery spike

**Phase:** Phase 7b: Skill discovery (v1.6)

**Part of:** [TASK62](TASK62-finding-unassigned-skills.md): Finding unassigned skills

**Status:** 🚧 In progress

**Depends on:** TASK61

Measure before building, as docs/spike-b01-results.md did for the MCP design. The spike does not wait for the other subtasks: it carries throwaway prototypes under `spike/discovery/` (not product code, with its own `go.mod` like `spike/b01`, so CI and the linter do not compile it): a server and hook variant that delivers the candidate texts of TASK62.8 (instruction wording and session-start cue), a ranked word search, a stand-in for the Searchable level (a list of IDs that `search_skills` is limited to), a `local` engine for that server in two routes (a model that runs in process, loaded from a file, either a static embedding model or a BERT-style model run in plain Go; and embeddings from a running runtime, each with a cosine comparison), and a script that embeds the library and the queries and compares them.

**Setup.** Each run uses a throwaway `QUIVER_HOME` and, for each assistant, an isolated home or profile (`CODEX_HOME`, a VS Code profile, and so on, as in the earlier spikes). Claude Code runs with project-level settings and `--setting-sources project`, as in TASK55.2, since its keychain login does not work in an isolated `CLAUDE_CONFIG_DIR`. The library has 250+ skills from at least three sources, all of them Searchable in the prototype. The task names a made-up product. Two skills fit it, both written for the spike: one named after the product, and one whose name and ID contain no word of the task, which only a description match or a match by meaning can reach. The prompt names neither Quiver nor a skill. The main case is a library in which no skill is listed: every skill is Searchable and the only thing the session-start text carries is the cue.

**Thresholds, fixed here, before any run.** 20 runs per cell. An assistant meets the threshold when at least 16 of 20 runs in the primary cell find the fitting skill, as TASK62 defines it (a route whose true rate is 60% passes about 5% of the time, one at 70% about 24%, one at 80% about 63%; the noise is part of the result). The primary cell is the candidate wording and cue of TASK62.8 in the library with no skill listed; the other cells inform and do not decide, except the control cell, which must not exceed 2 searches in 20 runs. Every cell records the model. A cell that misses may be run once more with changed wording as a new cell; the results file keeps both, and a threshold itself is never changed after a run without a note that says what changed and why.

**Cells, per assistant.** (a) the primary cell; (b) the baseline: today's texts in the same library with the skills *Not assigned*; (c) the candidate wording in a library with 16 listed skills, none of which fits, so the session-start text has a catalog; (d) a conversation of two turns: the first about the topic (for example an overdue task and a Slack channel), the second "write a draft about the last topic we discussed and send it", which does not name the topic; (e) the primary cell with the prompt written in Turkish; (f) the control: a plain question about the project, to which a search is not wanted. On Claude Code only, (g) the primary cell once more with the prototype's `local` engine, and (h) the reference: the fitting skill is listed (*On demand*) in the same library, so the rate of finding a skill by search can be read against the rate of using one that is listed. That is 160 runs on Claude Code and 120 on another assistant, plus retries. The results file states the runs made and the tokens spent. For v1.6 only Claude Code is measured (the 160 runs above); the cells of the other assistants (120 runs each) are run later by TASK68.2 with the same cells and thresholds, and the results file lists them as not yet measured. The results file also lists which assistants can be driven by a script (Claude Code, Codex, Cursor, VS Code, Antigravity); one that cannot is documented as not measured.

1. **Search route.** In how many runs of each cell is the fitting skill found (loaded with `get_skill` after a search, without asking), and through which of the two fitting skills; in how many runs of the control does the assistant search.
2. **Engines.** A query set kept in `spike/discovery/queries.json` and labelled before any scoring, built after the runs of item 1 so that it can hold the queries the assistants wrote: 30 queries of each of four kinds, the paraphrase of a skill without its words in English, queries as the assistants wrote them in the runs of item 1, the paraphrase in Turkish, and queries that fit no skill. Fifteen of each kind calibrate a cutoff per engine and per model (high enough that the queries that fit nothing return nothing), the other fifteen test; the split alternates down the file in the order the queries were written, before any scoring. With so few queries a difference of one is within chance, so the rules below are read together with the numbers. Compared: the matching of today, a ranked word search (BM25-style score over name, ID and description, exact and prefix name matches first, a cutoff), and the embedding models of two routes: from a running runtime nomic-embed-text, embeddinggemma and qwen3-embedding 0.6B, and in process the static embedding models potion-base-8M, potion-base-32M and potion-multilingual-128M (a tokenizer, the weight file, mean pooling and a normalisation, written in Go in the prototype, no cgo), and the BERT-style models all-MiniLM-L6-v2, gte-small, bge-small-en-v1.5 and e5-small-v2 run in plain Go (the same tokenizer, the weights, transformer layers, pooling and a normalisation). The measure for the three fitting kinds is the rate at which the fitting skill is in the top 5; for the kind that fits nothing it is the share of queries for which the engine returns nothing. Decision rules, fixed here: the ranked word search replaces the matching of today if its rate is not lower on any fitting kind and is higher on one, and its share on the no-fit kind is not lower; the route and the model of TASK62.6 and TASK62.7 are fixed in this order: (1) `local` ships in v1.6 only if its best model is higher than the ranked word search on at least two of the three fitting kinds on the test half; if not, TASK62.6 and TASK62.7 move to the Unscheduled list of tasks/README.md, TASK62.10 stops depending on them, and v1.6 ships the ranked word search alone; (2) the in-process route is the default if its best model reaches at least 90% of the best runtime model's rate on the test half of the three fitting kinds taken together, uses at most 500 MB of memory and is at most 150 MB to download, and otherwise the runtime route is the default; (3) within the default route the model is the one with the best rate on the test half of the three fitting kinds taken together, the smaller one on a tie, and a runtime model must use at most 2 GB of memory with the model loaded. The README gives the measured rates of `local` and of the ranked search side by side. **Deviations from the plan above (2026-11-21).** The first measurements (docs/spike-discovery-results.md) differ from it in four ways, each explained there. (1) The query set has 210 queries in six kinds, not 30 of each of four kinds: set B (60 English paraphrases and 30 queries that fit nothing) was added after the first comparison to widen the English test, the Turkish queries are reported on their own, and the queries of the kind assistant style were written by hand, because the runs of item 1 had not been made. (2) Rule (1) for the ranked word search is read together with the numbers: 26 of 27 queries that fit nothing return nothing, against 27 of 27, a difference of one query. (3) Rule (2) is read on English queries and on the word search fused with the model, as it ships, and no longer decides the route: the route of v1.6 is fixed as in process with all-MiniLM-L6-v2, and the runtime route and the models of other languages moved to backlog B20. (4) The install steps of the runtimes per system were not measured. The runs of item 1 and the cell with the `local` engine continue, and no threshold of item 1 was changed.
3. **Routes.** In process, for each model: the size of the download and on disk, the memory in use with the model loaded, the time to embed the whole library, the time per query, where the weights come from, their license and a hash to pin them to. Runtime (Ollama), as a reference for B20: the size on disk, the memory in use with each model loaded, the time of the first embedding after the model was idle, whether `/v1/embeddings` answers as TASK62.6 needs, and which models need a query or document prefix. The install steps per system, the need for root and a running instance on its default port are not part of v1.6: Quiver installs and starts no runtime (TASK62.7), and B20 measures them if that route is built.
4. **Result.** `docs/spike-discovery-results.md`: a table per assistant with the rates and whether the threshold is met, the engine comparison, the per-OS setup routes, and the decisions of item 2. TASK62.5 to TASK62.8 take their defaults from it.

**Done when:** the results file is committed, every number in it comes from a recorded run, every item above is answered for Claude Code (an item that could not be measured, including every other assistant, says so and why), and the thresholds in the file are the ones fixed here or carry the note described above.
