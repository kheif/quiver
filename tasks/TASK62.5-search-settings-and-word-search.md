# TASK62.5: Search settings and word search

**Phase:** Phase 7b: Skill discovery (v1.6)

**Part of:** [TASK62](TASK62-finding-unassigned-skills.md): Finding unassigned skills

**Status:** ✅ Done

**Depends on:** TASK61, TASK62.1, TASK62.4

One seam for all searching, so an engine is a plug-in and not a rewrite of every caller; the place where the search settings live; and a better `words` engine.

1. **Settings file.** `~/.quiver/state/search.json`, machine-local and never synced: the engine and the model files may differ between machines, and `config.json` is synced and merged key by key (data-model.md, "Synced home"). Keys: `version` (1) and `engine`. The only value now is `words`; TASK62.6 adds `local` and its block, and TASK62.7 adds `installed` and `offered`. A missing file or key means `words`. A value Quiver does not know, in a file it understands, warns once and uses `words`. A file with a newer `version` is refused in the wording of the existing messages (`internal/config/validate.go`, `internal/registry/registry.go`): `search.json has version N, but this quiver supports only up to 1: update quiver`. Quiver then neither reads nor rewrites the file, search runs as `words`, and the message appears in `quiver doctor` and once on stderr in the CLI or in `~/.quiver/logs/mcp.log` in the server, never on the MCP protocol channel. Search is best effort, so neither case stops a command.
2. **Commands.** `quiver search --engine <engine> <text>` overrides the engine for one run, and `quiver search` still needs text. Everything that is not a search lives in a new command group, `quiver engine`: `quiver engine` shows the engine and any problem found in the settings file, and `quiver engine use <engine>` writes the file; an unknown value is an error, and so is `use` on a file with a newer `version`, which writes nothing. TASK62.6 and TASK62.7 add `reindex`, `setup` and `remove`. The group is a command of its own and not a subcommand of `quiver search`, because `quiver search setup` would take the place of a search for the word "setup". The name is checked against every command and alias.
3. **Interface.** `library.Searcher` with `Search(ctx, query, skills) ([]Match, error)`, in `internal/library`, where `skills` is the set of skills to search; the callers choose it (item 5). `Match` stays `{skill, Rank}` plus an optional score; the scopes a skill is assigned in stay with the callers, as today.
4. **Ranked word search.** The `words` engine keeps its first three tiers (exact name, name prefix, name contains) as they are. Every other match gets a BM25 score as the spike measured it (`spike/discovery/words.go`; the parameters are in docs/spike-discovery-results.md): the name counts three times and the description once, the ID is not scored, terms are lower-cased, split at every character that is not a letter or a digit, stripped of stop words and lightly stemmed, with k1 = 1.2 and b = 0.75. The document frequencies and the average length come from the whole library, so a score means the same for any set of skills, and the set only limits which skills can match. A skill matches when its score reaches a cutoff, which TASK62.1 calibrated on the queries that fit nothing (9.784 on the spike's library and English queries) and this task checks again on the whole library; ties break by ID. The ranking is exactly what the spike measured: it adds no matching of word beginnings in descriptions and no folding of accents (backlog B21); a partial word of a name still matches through the name tiers. Words that most skills contain count little because of the weighting, and the cutoff keeps a long sentence from matching everything. Folding of case and accents stays as it is. TASK62.1 measured that the ranked search does better than the matching of today (docs/spike-discovery-results.md), so it replaces it.
5. **Callers.** `quiver search`, the `search_skills` tool and the panel use the configured engine, each on its own set of skills. `search_skills` searches the skills whose level in the folder is Searchable (TASK62.2: Searchable in the global or the project scope and not listed through the other), and returns nothing else: skills that are listed are already known to the assistant, and skills that are not assigned are not the user's choice. The engine ranks and caps within the set it is given, so a small Searchable set is never crowded out by other skills. `search_skills` returns at most 10 matches, where it returned 50: the assistant needs few, and each match carries its description. Every match is Searchable by construction, so the fields of a match stay as the tool returns them today (`assigned`, `scope`) and no level field is added: `assigned` is true and `scope` names the scope that holds it as Searchable (the project before the global one); `get_skill` loads it. This replaces the whole-library search of the tool; the release notes say so and why (TASK62.10). The description and result of the tool (TASK62.8 adds the cue to the description), including `more`, the number of matches left out by the cap, README.md (the command table and the MCP section), PROJECT.md (the tool table) and the website's `reference/mcp.md`, which describe the whole-library search, are updated here. `quiver search` and the panel keep searching the whole library, return everything, and show the level of each match. The panel keeps searching the whole library once and intersecting the result with the active view, as today.
6. **Failure never blocks.** An engine that cannot run falls back to `words` with one line saying so; search never returns an error for that reason.
7. **Display.** `quiver status` and `quiver doctor` show the engine and a problem found in the file. `quiver engine` shows the same. The setting is CLI-only in v1.6; the Settings page listed under "Later" in tasks/README.md gets it.
8. **Docs.** tasks/data-model.md and PROJECT.md describe `state/search.json`, the engine and the flags. The repository README, `quiver search --help`, `quiver engine --help`, the website's `reference/files.mdx` and the generated `reference/cli.md` (`web/README.md`) are updated.

**Done when:** tests cover a missing file, `words`, an unknown value (warn once, `words`), a newer `version` (refused, `words`, the message, `engine use` refused and nothing written), `--engine`, `engine use` and an unknown value of each, `quiver search` still needing text, `quiver engine` showing the engine and a problem in the file, the fallback of an engine that cannot run, the set of skills each caller searches (`search_skills` returning only Searchable skills of the folder, the CLI and the panel the whole library; a small Searchable set among many other skills), the cutoff (a query that fits nothing returns nothing, a long sentence does not match everything), a partial word of a name, the scores of a small Searchable set equal to the scores of the same skills in the whole library, the caps of the three callers (10, none, none), that the panel intersects engine results with every view, that nothing is written to stdout in the server; and the ranked search: the three tiers unchanged, a query of several words that no skill contains in full, ties, accents and case, and the top-5 rate of TASK62.1 on its test queries. An end-to-end test (TASK30) runs `engine use`, `search`, `status` and `doctor` through the binary.
