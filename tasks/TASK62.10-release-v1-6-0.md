# TASK62.10: Release v1.6.0

**Phase:** Phase 7b: Skill discovery (v1.6)

**Part of:** [TASK62](TASK62-finding-unassigned-skills.md): Finding unassigned skills

**Status:** ✅ Done

**Depends on:** TASK62.2, TASK62.3, TASK62.4, TASK62.5, TASK62.6, TASK62.7, TASK62.8, TASK62.9

1. README and help text cover every change of this phase, including the Searchable level and its flags, the engine, the flags of `quiver search`, the setup of the local model and the cue; each subtask has already updated its own documentation, and this task checks that nothing is missing. PROJECT.md's roadmap lists the phase under v1.6, and its new entry for finding skills in the library is worded distinct from "Search and a marketplace" and from the non-goal of hosting one.
2. The GitHub release notes list the changes since v1.5.0: the Searchable level; that `quiver new`, `quiver import` and the first-run import of `quiver init` now assign it instead of *On demand* (the MCP tool `create_skill` and `quiver fork` are unchanged), and that adding a source asks whether its skills are made Searchable; that `search_skills` now searches only Searchable skills, returns at most 10 matches, where it searched the whole library, returned 50 and asked before loading, and why (`quiver search --json` gains a field `level` next to `here`); that a registry with Searchable skills is written as version 3, which v1.5 refuses, and that v1.6 is a minor release because every v1.5 file is still read; the ranked word search (where it replaced the matching of today), the local engine (it runs inside Quiver, understands English only and needs one download of 91 MB) and its guided setup. **Why minor, and what the notes say first.** Under docs/releasing.md this is a minor release: nothing is removed or renamed, no input of an MCP tool changes, every v1.5 file is still read, and a v1.5 binary refusing a registry of version 3 repeats what v1.2 did with version 2 after v1.3 (TASK42). Two behaviours do change, and the first lines of the notes state them before the list: `search_skills` now searches only Searchable skills (a skill that is not assigned is found by `quiver search` and the panel, and `quiver add --source <name> --searchable --global` makes the skills of a source Searchable), and `quiver new` and `quiver import` assign *Searchable* instead of *On demand*. The notes give the reason: the assistant loads a Searchable skill without asking, so it searches only what the user chose.
3. **Upgrade check.** From a home made by the v1.5.0 binary (its golden home was created in TASK62.2), the new binary reads the version 2 `registry.json` and keeps it as it is until a Searchable entry is added, runs with no `state/search.json` as `engine: words`, `quiver doctor` is clean, and `cache/embeddings.json`, `cache/models/` exist only after the `local` engine was used.
4. **Measurement on the shipped build.** The primary cell, the control cell and the cell with the `local` engine of TASK62.1 are run again on Claude Code with the build that is released (the shipped texts, not the prototypes), and the rates are appended to docs/spike-discovery-results.md; the primary cell meets the threshold and the control stays within its limit (at most 2 searches in 20 runs), or the release waits (TASK62).
5. Tag `v1.6.0` (annotated) only after the maintainer confirms. The release workflow publishes to GitHub and npm and installs on clean machines.
6. **Website.** The pages that the subtasks wrote carry the "Next release" aside and badge of `web/README.md` until the release, have their sidebar entries (the guide "Finding skills"), and are committed only after the maintainer confirms; at the release the status marks follow it (see `web/README.md`).
7. **Repository.** The items of backlog B19 (repository settings and contributor files) are done or decided before the tag, since each release is published from this repository.
8. **Model file.** The download of TASK62.7 depends on one address. Before the tag the maintainer decides whether the project also keeps a copy of the model file in its release assets as a second pinned URL (TASK62.7, item 4), and the setup is run against the real addresses on a clean machine of each system that is available, with the result written in TASK62.7. If the copy is kept, the Apache-2.0 license text of the model goes with it.
9. **Security check.** Before the tag, the risks that this release adds are worked through and written in `docs/security.md` (this task creates the file; TASK70 completes it for the whole product): skills that the assistant loads without asking (the bulk question when a source is added, what `quiver update` shows for them, that `update_skill` cannot change them), the download of the model file and the loader that reads it (TASK62.7, TASK62.6), and that a search makes no network call. Each risk has its mitigation and its test, and one that is open blocks the tag. Backlog B07 (skills created through the MCP server) is decided here or left to TASK70 with the reason written down.
10. **Golden home.** After the tag, the golden home of v1.6.0 is made by running the released binary through the script of TASK62.2 and committed under `testdata/formats/v1.6.0/`; TASK63.8 upgrades from it.

**Done when:** the upgrade check, the measurement on the shipped build, the decision of item 8, the security check and the golden home are recorded, and the release workflow is green.
