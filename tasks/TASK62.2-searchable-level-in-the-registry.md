# TASK62.2: Searchable level in the registry

**Phase:** Phase 7b: Skill discovery (v1.6)

**Part of:** [TASK62](TASK62-finding-unassigned-skills.md): Finding unassigned skills

**Status:** Todo

**Depends on:** TASK61, TASK62.1

The fourth level of assignment (see TASK62): in a scope, a skill that is not listed and not loaded at session start, but that the assistant finds by searching. Assigning a skill is the user's statement that they trust it, so the assistant loads a Searchable skill without asking. This task starts after the spike (TASK62.1): TASK62.8 changes what `quiver new` and `quiver import` assign for every user, and that is right only if the measured rate of finding a Searchable skill meets the threshold of TASK62 on Claude Code.

TASK62.2 to TASK62.4 build the level together. This task stores it: the registry, the level of a skill across the two scopes, and the format rule for every file Quiver writes. TASK62.3 assigns it (the commands and the question when a source is added), TASK62.4 delivers it (the MCP server, every reader of assignments, the panel, the docs), and TASK62.8 makes it the default for the skills the user makes, together with the cue that tells the assistant to search.

1. **Registry.** `registry.json` gets a `searchable` list next to `global` (every folder) and one in each project next to `skills`; both are omitted when empty. A skill is in at most one of the two lists of a scope: Searchable, or served (`global` or `skills`, with `alwaysOn` as a subset, as today). The assigning calls move a skill and never leave it in two lists. A file that has a skill in two lists, which a merge of two machines can produce (one adds it as Searchable, the other as On demand or always on), is normalised when it is read and when it is merged and never rejected: the skill keeps its most served level (always on, then listed, then Searchable). `Merge` removes the skill from the `searchable` list first and only then drops the always-on marks of skills that are not served (`keep` in `internal/registry/merge.go`), so a skill that one machine made always on and the other Searchable stays always on. **Version.** The version written is 3 when any `searchable` list is non-empty and 2 otherwise, so a registry that has no Searchable skill, or no longer has one, stays readable by v1.5. Both writers compute it: `Write` in `internal/registry`, which now always writes `CurrentVersion`, and `Merge`, whose result `quiver sync` writes directly (`internal/homesync`), so a merged file never carries version 2 with a `searchable` list. v1.6 reads versions 2 and 3 and refuses version 4 in the wording of the existing messages (TASK67); v1.5 refuses version 3. `quiver sync` merges the new lists as sets, like the others. tasks/data-model.md describes all of it, and TASK67 lists registry version 3.
2. **Levels across the two scopes.** A skill can be Searchable in one scope and served in the other. In a folder its level is its most served level across the global and the project scope (always on, then listed, then Searchable). The cue, `get_skill` and `search_skills` use that level: a skill that is listed in the folder through either scope is not searched, because the assistant already knows it.
3. **Format rule and golden homes.** From this task on, every file that Quiver writes in the Quiver home carries a format version from the release that introduces it (tasks/decisions.md gets a row for the rule), and a file from a newer Quiver is refused with the version needed, as the state file already is. A file under `cache/` is derived data and is the exception: another format version is ignored and rebuilt (TASK62.6), not refused. The golden home of a release lives under `testdata/formats/<version>/` and is made by running that release's binary through one script of commands (init, source add, add, add --always, a project). The script removes `local/.git` from the home before it is committed, since a repository cannot be committed inside this one, and the test makes a fresh repository in its copy of the home. This task writes the script, the home of v1.5.0 and the test that copies a home, runs the current code on it and checks the upgraded files and a clean `doctor`; TASK67 extends the same layout to the older releases and to the files that exist already.

**Done when:** tests cover the registry (a version 2 file read as before; a file with a searchable entry written as version 3, by `Write` and by `Merge`, and one whose last searchable entry was removed written as version 2; empty lists omitted; a version 4 file refused; a golden home made by the v1.5.0 binary, created in this task under `testdata/formats/v1.5.0/` as item 3 says, read and left unchanged; a skill in two lists of a scope normalised to its most served level on read and in two merges of two machines (Searchable against On demand, and Searchable against always on), and never in two lists after an assigning call; global and project scopes; the level of a skill that is Searchable in one scope and served in the other; a project without a folder).
