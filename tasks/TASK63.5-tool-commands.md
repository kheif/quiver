# TASK63.5: Tool commands

**Phase:** Phase 7c: Tool bundles (v1.7)

**Part of:** [TASK63](TASK63-tool-bundles.md): Tool bundles

**Status:** Todo

**Depends on:** TASK63.4, TASK58.4

The commands that use the engine. The name `quiver tool` is the working name; it is settled here, with a check that it clashes with no command or alias.

1. `quiver tool list`: the bundles of all sources and which are installed, in which scope.
2. `quiver tool add <id>`, with the target flags of `quiver add` (`--global`, or `--project <folder>`; the default is this project, and a project that is not registered is registered after a question, as for `add`): checks `requires` (a missing runtime is named, with how to get it, and nothing runs), shows the **consent text**, which starts with one plain sentence (what will be installed, how many settings it adds to which assistants, and the command that undoes it) before the technical lines, then runs the install command and writes the components. The consent text lists every command (the argv as it will run, with the first element resolved to the absolute path of the program, looked up in `PATH` once, when the text is made, and run from that path; the working directory), every entry and file (path, scope, assistant), every environment variable the tool needs, and the commit the bundle is pinned to. Nothing runs before a yes, and what runs comes from the commit the text printed: the source is not updated between the text and the run, so the commands and files cannot differ from what was shown. `--yes` answers every question of the command, but only together with `--commit <sha>`, the commit that the consent text printed (for example from `--dry-run`); without it, or with another commit, `--yes` is refused, because a first add has no earlier view and `--yes` alone would run commands that nobody saw. It is also refused for a bundle whose manifest changed since the user last saw it, and for a local directory, which has no commit: there the user answers the questions.
3. `quiver tool remove <id>`: shows what will be reversed, asks, runs the uninstall command that the ledger holds (the one the user agreed to, not the one in today's manifest), reverses the ledger. Data the tool made (a database, `graphify-out/`) is listed and left alone; the manifest may name a purge flag of the tool's own uninstall, which only `--purge` passes.
4. `quiver tool status [<id>]`: per component intact, changed, missing; the runtime found; the output of the manifest's status command, shown as text and sanitized (TASK58.4's rules); and the size of the instruction blocks Quiver wrote, in characters and as an estimate of tokens, since they are part of every session's cost.
5. `quiver tool update <id>`: the preview of diffs of sources, for the manifest, and a yes whenever a command, an entry or a file of the bundle changes (the consent text again, for what changed; `--yes` follows the rule of item 2), then the upgrade command and a rewrite of changed components.
6. **Kinds.** Adding a bundle whose `kind` another installed bundle has: a warning that names both and asks.
7. **A command that fails** leaves the ledger as it was: components are written only after the install command succeeded, and reversed if a later write fails. The home lock is not held while a command of the manifest runs, because it can take long and may start `quiver` itself; it is taken only to write the ledger and the entries.
8. `--dry-run` on `add`, `remove` and `update` prints the consent text and changes nothing. `quiver doctor` and `quiver status` report changed or missing entries and a missing runtime. Exit codes, `--json` and help text follow the other commands.
9. **Other readers of the ledger.** `quiver source remove` and the panel's `x` refuse while a bundle of that source is installed, as they do for assigned skills; `quiver doctor` reports an installed bundle whose source or manifest is gone; `quiver update <source>` reports a newer manifest (TASK63.2); `quiver status` lists the installed bundles. `quiver projects forget` refuses while a bundle is installed in that project (`quiver tool remove` first), because the files the bundle wrote stay in the folder. `quiver projects split` does not copy the ledger: the copy starts with no bundle, `quiver doctor` reports the files in it that the original's bundle wrote, and `quiver tool add` in the copy takes them over.

**Done when:** tests and an end-to-end test (TASK30) cover each command, a declined consent, `--yes` on a changed manifest, a failing install command, a failing write after a successful one, two bundles of one kind, and `--dry-run`; `--yes` without `--commit`, with another commit and with the right one; `tool update` waiting for a yes when a command changes; `remove` after the manifest was deleted (the uninstall command of the ledger runs); `source remove` refused while a bundle is installed; and no lock held while a command runs (a command that calls `quiver status` does not hang).
